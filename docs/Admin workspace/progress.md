## Decisions to resolve

- [x] **Confirm owner versus admin powers**: Owner has full account, workspace, and team governance; Admin has full business data, record, page, and dashboard authoring rights without privilege escalation to owner. Destructive dataset deletion is protected by typed confirmation dialogs in the UI and safe collection drops.
- [x] **Confirm workspace-wide publication, personal preferences, and drafts**: Workspace-wide `published: boolean` and `nav_order: integer` persisted in `app_pages`. Draft pages are visible only to owners and admins. Normal members only list/view published pages for datasets where they hold `read` permission, enforced directly by PocketBase hooks, collection rules, and pre-pagination query filters across all read and realtime paths.
- [x] **Choose the initial second page view and dashboard widgets**: Initial second view is `kanban` (with `groupByField` and `cardFields`), alongside `table` and `master_detail`. Initial dashboard widgets are `kpi` (metric counts/sums), `table` (recent records with field selectors), and `list`.
- [x] **Decide the policy for existing PocketBase collections and external schema changes**: Existing PocketBase collections are automatically synced into `schema_definitions` via `RegisterSyncHooks`. File fields are upgraded to `Protected: true` via migration `1799000000_ensure_protected_file_fields.go`. Safe optional field additions are supported without data loss. Destructive drops require typed confirmation.
- [x] **Agree on the acceptance scenario and release owner**: Detailed in [acceptance-scenario.md](acceptance-scenario.md) with an 8-step journey covering bootstrap, invitations, multi-field datasets, page authoring, dashboard configuration, multi-session isolation, safe evolution/unpublishing, and confirmed deletion / backup restoration.

## Blockers and release limitations

- **[Open] Browser end-to-end journey not yet run.** The plan calls for a full browser journey (dataset creation, page authoring, file download, two-session conflict recovery, member's denied access). Current acceptance tests exercise HTTP APIs; interactive browser automation (Playwright/Cypress) is not part of the current test harness.
- **[Open] Backend test suite re-run pending.** The reviewer stopped the backend run mid-flight; a fresh `go test -count=1 ./backend/internal/...` has not completed since migration 1799 and `RegisterDashboardRevisionHook` were added.
- Verification scope: Automated tests thoroughly verify backend HTTP API, token-based protected file access (`/api/files/token`), PocketBase SQLite queries and collection rules, pre-pagination filtering, realtime SSE delivery/suppression, migration scaling, SDK client error propagation, and React component DOM rendering.
- Single-tenant deployment scope: Features are tailored for single-tenant PocketBase instances; hosted multi-tenant provisioning and public unauthenticated sites remain outside the current scope as defined in [plan.md](plan.md).
- Destructive schema drops require explicit schema ID typing in the UI to prevent inadvertent data loss; cascading collection drops will drop associated records in PocketBase.
